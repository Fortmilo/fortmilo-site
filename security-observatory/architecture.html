Architecture and security

Runs inside Salesforce with a narrow evidence boundary.

The Observatory is built around Lightning Web Components, Apex orchestration, scanner classes, subscriber-controlled platform access and sanitised in-org evidence.

Execution path

One Apex-owned scanner plan

LWC dashboard→SecurityObservatoryController→SecurityScanService→Scanner classes→SOQL, Tooling API and metadata reads
Scanner output→Security_Scan__c→Findings, metrics, details and assets→Dashboard DTOs→Safe drill-down and export

How it stays safe

Six deliberate controls

Read-only by design

No token revocation, API blocking, permission removal, endpoint change, certificate rotation or production security write-back.

Runs in your organisation

Scanning executes as Apex inside the subscriber Salesforce organisation and retained evidence stays there.

No third-party evidence destination

The only supported callout pattern is a subscriber-authenticated self-callout to that organisation's own Salesforce Tooling API.

No secrets stored

No access tokens, refresh tokens, session IDs, client secrets, certificate bodies, private keys, raw headers or raw IP values.

Least-privilege access

Tooling-backed evidence uses subscriber-owned authentication and separate least-privilege principal access rather than a hard-coded credential.

Documented kill switch

The subscriber can revoke or remove the self-callout principal. Tooling-backed evidence then degrades to a visible non-assessed state rather than a false clean result.

No data egress to FortMilo Lab.

Evidence is queried, sanitised and stored inside the subscriber Salesforce organisation. FortMilo Lab does not receive scan evidence, credentials or organisation data.

Self-callout prerequisite

Subscriber-owned authentication

Core SOQL-backed evidence can run without Tooling API authentication. Tooling-backed families require subscriber-specific setup using an Auth Provider, External Client App, External Credential, Named Credential and principal.

The core package must not own or overwrite subscriber OAuth configuration. Principal access is granted separately after the subscriber creates and authenticates the principal.

Missing, unauthenticated or insufficient setup must remain visible as a bounded non-clean state with a safe next action.

Public source boundary

Curated, not mirrored

The private implementation and its working history are not exposed directly. The public application repository is intended for selected sanitised source, architecture, setup guidance, synthetic examples, validation evidence and contribution material.

Package creation, installation proof and public distribution are claimed only when the relevant evidence exists.
